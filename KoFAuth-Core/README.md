# KoFAuth-Core

Реализация контрактов [`KoFAuth-API`](../KoFAuth-API): конфигурация, персистентность,
кэш, криптография, шина событий, пулы потоков.

**В модуле нет ни одного импорта `org.bukkit.*` или `com.velocitypowered.*`** — Core
тестируется обычным JUnit без запуска Minecraft-сервера.

---

## Что готово

| Пакет | Классы | Назначение |
|-------|--------|-----------|
| `concurrent` | `AsyncExecutors`, `NamedThreadFactory` | Четыре раздельных пула с ограниченными очередями |
| `config` | `YamlConfigurationService`, `YamlDocument` | YAML + переменные окружения + горячая перезагрузка |
| `security` | `PasswordHasher`, `PasswordPolicy`, `AesCipher`, `JwtProvider`, `TokenGenerator` | BCrypt, AES-256-GCM, JWT HS512, криптостойкие коды |
| `database` | `DatabaseManager`, `SqlExecutor` | HikariCP + Flyway, подготовленные выражения, транзакции |
| `cache` | `CacheProvider`, `RedisCacheProvider`, `NoopCacheProvider` | Redis через Lettuce с деградацией при отказе |
| `event` | `SimpleEventBus`, `RedisEventBridge` | Локальная шина + межпроцессная доставка |

Ещё не реализованы: JDBC-репозитории, сервисный слой, сборка графа зависимостей
(`KoFAuthCore`). Это следующий шаг этапа 3.

## Семь решений, которые стоит знать

### 1. Пулы разделены по типу нагрузки

`kofauth-db`, `kofauth-io`, `kofauth-mail`, `kofauth-sched`. Через один пул зависший
SMTP-сервер съел бы все потоки, и игроки перестали бы входить: письмо идёт секунды,
запрос к базе — миллисекунды, и ставить быстрые задачи в очередь за медленными нельзя.

Очереди **ограничены**. Неограниченная очередь при недоступной базе копит задачи до
`OutOfMemoryError`; ограниченная отвергает лишнее, future завершается исключением, а
игрок видит «сервис временно недоступен». `CallerRunsPolicy` здесь недопустим:
вызывающим часто оказывается главный поток Minecraft.

### 2. Перезагрузка — всё или ничего

`ConfigurationService.reload()` сначала читает и разбирает все девять файлов и только
потом публикует их атомарной подменой ссылки. Ошибка в одном файле отменяет
перезагрузку целиком. Иначе администратор видит сообщение об ошибке в одном файле и
не догадывается, что восемь других уже применились.

`DatabaseManager.reload()` следует тому же правилу на уровне ресурса: создаёт новый
пул, проверяет его живым соединением, и лишь затем подменяет и закрывает старый.
Опечатка в пароле базы не оставляет сеть без аутентификации — это проверено тестом
`неудачная_перезагрузка_оставляет_рабочим_прежний_пул`.

### 3. Постоянное время ответа при неверном пароле

`PasswordHasher.wasteTime()` выполняет **ровно одну** операцию `verify` против заранее
вычисленного хэша той же стоимости. Вызывается, когда аккаунта не существует: без
этого несуществующий ник отвечает за миллисекунду, а существующий — за сотню, и
разница выдаёт наличие аккаунта даже при одинаковом тексте ошибки.

Вычислять хэш прямо в этом методе было бы ошибкой: хэширование плюс проверка стоят
вдвое дороже реального пути, и утечка по времени осталась бы, только с обратным знаком.

### 4. Секреты по сети не ездят

`RedisEventBridge` отправляет не сам объект события, а `RemoteEvent` — плоский набор
скалярных атрибутов. Доменные события несут внутри `Account` с `passwordHash`, и
сериализация «как есть» разложила бы хэши всей сети по каналу Pub/Sub.

Поля набираются **белым списком** для каждого типа события. Забыть вычеркнуть секрет
негде: неописанный тип просто не уезжает и остаётся локальным. Проверено тестами
`хэш_пароля_не_попадает_в_канал` и `полный_адрес_не_попадает_в_канал`.

### 5. Отказ Redis не роняет аутентификацию

Каждая операция `RedisCacheProvider` обёрнута так, что исключение превращается в
«нет данных» и запись в лог. Для вызывающего промах кэша и отказ кэша — одно событие,
после которого он идёт в MySQL.

Единственное исключение — `setIfAbsent`: при отказе он возвращает `false`. Выдать
ложное подтверждение занятой блокировки опаснее, чем отказать в операции.

`NoopCacheProvider` подставляется, когда Redis выключен. Он не `final` намеренно —
служит базой для частичных реализаций и тестовых двойников.

### 6. Скользящее окно считается на Lua

Чистка окна, добавление события и подсчёт выполняются одним скриптом. Тремя
отдельными командами это было бы неатомарно: параллельные запросы успевали бы
посчитать себя до того, как их учли.

Окно именно скользящее, а не фиксированное: при фиксированном лимит «10 в минуту»
позволяет сделать 20 запросов на стыке двух минут.

### 7. Сконкатенировать SQL нечем

`SqlExecutor` не имеет ни одного метода, принимающего готовую строку с подставленными
значениями — только SQL с placeholder'ами и отдельный массив параметров. Это
единственная работающая защита от инъекций: не «не забывать экранировать», а не иметь
возможности ошибиться.

Нарушение уникального ключа выделено в `DuplicateKeyException`: гонка двух регистраций
одного ника — не отказ базы, а штатный исход, который сервис обязан показать как
«ник занят».

## Тесты

```bash
./mvnw -pl KoFAuth-Core test        # 133 модульных
./mvnw -pl KoFAuth-Core verify      # + 25 интеграционных (нужен Docker)
```

Интеграционные тесты поднимают настоящие MySQL 8 и Redis 7 через Testcontainers.
Проверяется то, что моками проверить нельзя: применение миграций, работа соединения
в UTC, атомарность `GETDEL`, поведение скользящего окна, доставка Pub/Sub.

### Если Testcontainers не находит Docker

Симптом: `Could not find a valid Docker environment`, при том что `docker ps` работает.

Причина: клиент `docker-java` запрашивает `/v1.32/info`, а Docker Engine 29 принимает
только API 1.40 и выше. Движок отвечает `400` с пустым телом, и Testcontainers считает,
что Docker недоступен.

Решение уже в `pom.xml` — свойство `docker.api.version` (по умолчанию `1.44`)
передаётся в forked JVM как системное свойство `api.version`. Для движка старше
Docker 25 переопределите:

```bash
./mvnw verify -Ddocker.api.version=1.41
```
