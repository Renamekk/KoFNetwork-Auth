# KoFAuth — эксплуатация

Docker, наблюдаемость, резервные копии и что делать, когда что-то сломалось.

---

## 1. Быстрый старт в Docker

```bash
cd docker
cp .env.example .env
```

Заполните `.env`. Два ключа обязательны — без них ничего не запустится:

```bash
openssl rand -base64 32   # ENCRYPTION_KEY
openssl rand -hex 32      # JWT_SECRET
```

```bash
docker compose up -d              # MySQL, Redis, WebAPI
docker compose --profile bots up -d   # плюс Telegram и Discord
```

Проверка:

```bash
curl -s localhost:8080/actuator/health | jq
```

Личный кабинет — `http://localhost:8080/`, Swagger — `/swagger-ui.html`.

### Что где лежит

| Сервис | Назначение |
|---|---|
| `mysql` | Источник истины. Том `mysql-data` |
| `redis` | Сессии, кэш, межпроцессная шина. Сохранение на диск **выключено** |
| `webapi` | REST API + личный кабинет |
| `telegram`, `discord` | Боты, профиль `bots` |

Redis настроен без persistence намеренно: там только сессии и кэш. Потеря при
перезапуске означает повторный вход игроков, а не потерю данных.

## 2. Наблюдаемость

### Health

`GET /actuator/health` — единственный открытый наружу эндпоинт actuator.
Остальные раскрывают конфигурацию и метрики, которые незачем показывать миру.

```json
{
  "status": "UP",
  "components": {
    "kofauth": {
      "status": "UP",
      "details": {
        "database": "up",
        "databaseConnections": "2/10",
        "databaseAwaiting": 0,
        "cache": "redis"
      }
    }
  }
}
```

**Недоступность Redis не делает статус `DOWN`.** Кэш — ускоритель: без него
система работает по MySQL, теряя скорость и связность между процессами, но
продолжая обслуживать вход. Помечать такое как `DOWN` значило бы заставить
оркестратор перезапускать исправный контейнер. В деталях это видно как
`"cache": "degraded"` — повод разобраться, но не повод выводить узел из ротации.

Недоступность MySQL — наоборот: аутентификация невозможна, трафик слать нельзя.

### На что смотреть

| Признак | Где | Что означает |
|---|---|---|
| `databaseAwaiting` > 0 постоянно | health | Пул мал либо запросы медленные |
| `Очередь пула ... переполнена` | лог | Хранилище недоступно, задачи отбрасываются |
| `Буфер аудита переполнен` | лог | База не принимает записи, аудит теряется |
| `Потеряно записей аудита` | лог | Пачка не записалась — след событий неполон |
| `Повторное использование токена` | лог + `security_logs` | Утечка refresh, цепочка отозвана |
| Рост `login_history` с `success=0` | SQL | Перебор паролей |

Полезные запросы:

```sql
-- Перебор по одному аккаунту за час
SELECT username_attempt, COUNT(*) AS n
FROM login_history
WHERE success = 0 AND created_at > DATE_SUB(UTC_TIMESTAMP(3), INTERVAL 1 HOUR)
GROUP BY username_attempt HAVING n > 10 ORDER BY n DESC;

-- Перебор ников с одного адреса
SELECT INET6_NTOA(ip) AS addr, COUNT(DISTINCT username_attempt) AS names
FROM login_history
WHERE success = 0 AND created_at > DATE_SUB(UTC_TIMESTAMP(3), INTERVAL 1 HOUR)
GROUP BY ip HAVING names > 5 ORDER BY names DESC;

-- Инциденты за сутки
SELECT event_type, COUNT(*) FROM security_logs
WHERE severity = 'CRITICAL' AND created_at > DATE_SUB(UTC_TIMESTAMP(3), INTERVAL 1 DAY)
GROUP BY event_type;
```

## 3. Резервное копирование

```bash
docker compose exec -T mysql \
  mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers kofauth \
  | gzip > kofauth-$(date +%F).sql.gz
```

`--single-transaction` снимает согласованный снимок без блокировки таблиц —
InnoDB это позволяет, и игроки не заметят снятия копии.

⚠️ **Дамп без `ENCRYPTION_KEY` наполовину бесполезен.** Секреты TOTP и
OAuth-токены Discord зашифрованы AES-256-GCM: восстановив базу с другим ключом,
вы получите аккаунты, у которых второй фактор не работает и не отключается
штатным путём. Ключ храните вместе с копией, но не в ней.

Redis не бэкапится: восстанавливать сессии незачем.

Проверка восстановления (делать регулярно — непроверенная копия не копия):

```bash
docker run --rm -d --name restore-test -e MYSQL_ROOT_PASSWORD=t -p 33062:3306 mysql:8.0
gunzip -c kofauth-2026-08-01.sql.gz | docker exec -i restore-test mysql -uroot -pt kofauth
```

## 4. Обновление

Схема развивается только новыми миграциями: `V1` и `V2` уже посчитаны Flyway
по контрольной сумме, и правка применённого файла остановит запуск.

```bash
git pull
docker compose build
docker compose up -d
```

Миграции применит первый стартовавший процесс; остальные подождут на блокировке
`flyway_schema_history`.

**Порядок при обновлении игровой сети:** сначала прокси (он применяет миграции),
затем Limbo, затем игровые серверы.

## 5. Разбор типичных ситуаций

### Игроки не могут войти, в логе «Очередь пула kofauth-db переполнена»

База не отвечает или пул исчерпан. Проверьте `databaseAwaiting` в health и
`SHOW PROCESSLIST` в MySQL. Если запросы висят на блокировках — ищите долгую
транзакцию. Если пул просто мал — поднимите `mysql.pool.maximum-size`, но
помните: больше соединений не делает MySQL быстрее, они начинают конкурировать.

### `Redis недоступен, работаем без кэша`

Сеть продолжает работать, но сессии перестали быть общими между прокси: игрок,
вошедший через один, для второго не аутентифицирован. На сети из одного прокси
терпимо, на нескольких — нужно чинить срочно.

### Игрока выкидывает сразу после входа

Смотрите `security_logs` на `SESSION_IP_MISMATCH`. Обычно это мобильный интернет
со сменой адреса. Лечится `auth.session.bind-to-ip: false` — но это ослабляет
защиту от угона сессии, решайте осознанно.

### Плагин не виден Velocity

Проверьте, что дескриптор попал в jar:

```bash
unzip -p KoFAuth-Velocity-1.0.0-SNAPSHOT.jar velocity-plugin.json
```

Пусто — сборка шла без `-proc:full` (с JDK 22+ аннотационные процессоры с
classpath не запускаются). Подробности в [журнале разработки](00-DEVELOPMENT-LOG.md), §5.4.

### Забыт пароль администратора

```bash
# В консоли Velocity
auth resetpassword Ник НовыйПароль123
```

Консоль имеет все права безусловно — аккаунт для неё не нужен.

## 6. Чек-лист перед публичным запуском

- [ ] `ENCRYPTION_KEY` и `JWT_SECRET` заданы через окружение, а не в файлах
- [ ] Ключ шифрования сохранён вне сервера вместе с процедурой восстановления
- [ ] MySQL и Redis не смотрят в интернет (уберите `ports` из compose)
- [ ] `forwarding.trust-proxy-header` включён **только** если перед сервисом
      действительно стоит обратный прокси
- [ ] `player-info-forwarding` и `secret` настроены на всех Paper-серверах
- [ ] `try` в `velocity.toml` указывает на Limbo, а не на лобби
- [ ] `bcrypt-cost` соответствует железу: замерьте время входа под нагрузкой
- [ ] Резервное копирование настроено **и проверено восстановлением**
- [ ] `captcha.enabled` и `antibot.enabled` включены
- [ ] Настроен SMTP — без него не работает восстановление пароля
- [ ] `cors.allowed-origins` задан, если кабинет на отдельном домене
- [ ] TLS терминируется перед WebAPI (nginx, Caddy, Cloudflare)

## 7. Ориентиры по нагрузке

Заложенные при проектировании цели:

| Параметр | Значение |
|---|---|
| Одновременных игроков | 5 000 |
| Входов в секунду | 40 |
| Задержка проверки сессии | p99 < 25 мс |
| Блокировка главного потока Minecraft | 0 мс |

Узкое место при росте — **BCrypt**: при cost 12 проверка занимает 100–250 мс.
40 входов в секунду требуют примерно 4–10 полностью занятых ядер. Если входов
больше, снижать cost не следует — правильнее добавить узлов: пулы и сессии уже
рассчитаны на горизонтальное масштабирование, состояние лежит в Redis, а не
в памяти процесса.

Рост таблиц при 5 000 CCU: `login_history` ≈ 15 тыс. строк в сутки (~2 МБ),
`security_logs` ≈ 40 тыс. (~8 МБ). Записи `INFO` ротируются через 90 дней,
`WARNING` и `CRITICAL` — никогда.
