# KoFAuth — развёртывание

Как поставить собранные артефакты и что настроить, чтобы сеть заработала.

---

## 1. Артефакты

```bash
./mvnw clean install -DskipITs
```

| Файл | Куда |
|------|------|
| `KoFAuth-Velocity/target/KoFAuth-Velocity-1.0.0-SNAPSHOT.jar` | `velocity/plugins/` |
| `KoFAuth-Paper/target/KoFAuth-Paper-1.0.0-SNAPSHOT.jar` | `paper-limbo/plugins/` и `paper-lobby/plugins/` |

Один и тот же jar Paper ставится и на Limbo, и на игровые серверы — роль задаётся
параметром `mode` в `paper.yml`.

---

## 2. Обязательные секреты

Без них KoFAuth **не запустится**. Это намеренно: сервер, поднявшийся с пустым
ключом AES или JWT, молча раздаёт подделываемые токены, и такой отказ обнаружится
не скоро.

```bash
openssl rand -base64 32   # security.encryption.key
openssl rand -hex 32      # security.jwt.secret
```

В производственной среде задавайте их переменными окружения, а не файлом:

```bash
export KOFAUTH_SECURITY_ENCRYPTION_KEY="..."
export KOFAUTH_SECURITY_JWT_SECRET="..."
export KOFAUTH_DATABASE_MYSQL_PASSWORD="..."
```

⚠️ **Потеря `encryption.key` делает нечитаемыми секреты TOTP и токены Discord.**
Храните его вместе с резервной копией базы — иначе восстановленный дамп окажется
наполовину бесполезным.

---

## 3. Порядок запуска

1. **MySQL и Redis.**
2. **Velocity.** Прокси стартует первым и применяет миграции — Paper-серверы
   подключаются к готовой схеме.
3. **Limbo (Paper, `mode: LIMBO`).**
4. **Лобби и игровые серверы (Paper, `mode: BACKEND`).**

---

## 4. Настройка Velocity

`velocity.toml`:

```toml
player-info-forwarding-mode = "modern"
online-mode = false          # для нелицензионных аккаунтов

[servers]
limbo-1 = "127.0.0.1:30001"
lobby-1 = "127.0.0.1:30002"
try = ["limbo-1"]            # первым делом — Limbo, не лобби
```

`plugins/kofauth/velocity.yml`:

```yaml
limbo:
  servers: [limbo-1]
lobby:
  servers: [lobby-1]
```

**`try` обязан указывать на Limbo.** Если там окажется лобби, игрок при подключении
на мгновение попадёт на боевой сервер до того, как отработает маршрутизация.

---

## 5. Настройка Paper

На Limbo-сервере `plugins/KoFAuth/paper.yml`:

```yaml
mode: LIMBO
limbo:
  world-name: kofauth_limbo
```

`server.properties` Limbo:

```properties
online-mode=false
max-players=1000
view-distance=2
simulation-distance=2
```

Малый радиус прорисовки существен: в Limbo смотреть не на что, а при заходе
ботнета каждый чанк — это трафик и память.

На игровых серверах:

```yaml
mode: BACKEND
backend:
  verify-session: true
```

---

## 6. Проверка защиты от обхода прокси

`verify-session: true` на бэкенде — вторая линия обороны. Первая — сетевая:

```properties
# server.properties каждого Paper-сервера
online-mode=false
```

плюс `paper-global.yml`:

```yaml
proxies:
  velocity:
    enabled: true
    online-mode: true
    secret: <тот же, что в velocity.toml>
```

Без корректного `secret` любой сможет подключиться к бэкенду напрямую под чужим
ником. `verify-session` это перехватит, но полагаться на одну лишь проверку сессии
не стоит — правильная настройка форвардинга обязательна.

---

## 7. Что проверить после запуска

| Проверка | Ожидаемо |
|----------|----------|
| Зайти новым ником | Попадание в Limbo, приглашение зарегистрироваться |
| Написать в чат до входа | Сообщение не проходит |
| Выполнить `/help` до входа | Команда отклонена |
| Сломать блок в Limbo | Блок цел |
| `/register пароль пароль` | Аккаунт создан, перевод в лобби |
| Переподключиться | Вход без пароля (сессия действует) |
| `/login неверный` ×3 | Временная блокировка |
| `SELECT * FROM login_history` | Записи и об успехах, и о неудачах |

## 8. CAPTCHA

Работает при `captcha.enabled: true` в `captcha.yml`. Два режима:

| Тип | Как выглядит |
|-----|--------------|
| `GUI_GRID`, `BLOCK_SELECT`, `BUTTON_CLICK` | Окно с сеткой предметов, ответ — клик по нужной ячейке |
| `TEXT_INPUT` | Код в чате, ответ командой `/captcha <код>` |

Задача выдаётся при заходе в Limbo (по правилам `require-on`) и после неудачных
попыток входа, когда прокси переводит игрока в состояние `CAPTCHA_REQUIRED`.

Закрыть окно на Escape нельзя — оно переоткрывается, и попытка при этом не
расходуется. После неверного ответа выдаётся **новая** сетка, а не та же самая:
повтор одной раскладки позволил бы перебрать её кликами за несколько секунд.

Размер сетки задаётся как `gui.grid-size × gui.rows` и округляется вверх до кратного
девяти — Bukkit не создаёт инвентарь другого размера.

## 9. Административные команды

`/auth` на прокси. Права берутся из RBAC в базе, а не из `permissions.json`
Velocity: роли общие для всей сети и меняются из панели, а два источника истины
неизбежно разойдутся. Консоль имеет все права безусловно.

| Подкоманда | Право | Действие |
|-----------|-------|----------|
| `reload` | `kofauth.admin.reload` | Перечитать конфигурацию |
| `info` | `kofauth.admin.info` | Состояние базы, кэша, пулов |
| `player <ник>` | `kofauth.admin.player` | Сведения об аккаунте |
| `lock` / `unlock <ник>` | `kofauth.admin.lock` | Блокировка; при снятии сбрасывается счётчик неудач |
| `resetpassword <ник> <пароль>` | `kofauth.admin.resetpassword` | Сброс пароля, все сессии разрываются |
| `forceverify <ник>` | `kofauth.admin.forceverify` | Подтвердить почту вручную |
| `sessions` / `devices` / `logs <ник>` | соответствующие | Просмотр |

Выдать права администратору:

```sql
INSERT INTO user_roles (account_id, role_id)
SELECT u.id, r.id FROM users u, roles r
WHERE u.lower_username = 'ваш_ник' AND r.name = 'admin';
```

Любое действие над чужим аккаунтом попадает в `security_logs` с `actor_id`:
по журналу видно не только что произошло, но и кто это сделал.

## 10. Почта

Включается в `mail.yml` (`enabled: true` + настройки SMTP). Пароль SMTP задавайте
переменной `KOFAUTH_MAIL_SMTP_PASSWORD`.

Команды игрока (на прокси):

| Команда | Действие |
|---|---|
| `/email` | Состояние привязки |
| `/email <адрес>` | Привязать и получить код |
| `/email verify <код>` | Подтвердить |
| `/email resend` | Выслать код заново (под ограничением скорости) |
| `/email unlink` | Отвязать |

**Непроверенная почта не даёт ничего.** С неё нельзя восстановить пароль и на неё
не уходят уведомления — иначе привязка чужого адреса стала бы способом угона.

### Восстановление пароля

`requestPasswordReset` отвечает успехом **всегда** — и для существующего ника, и
для несуществующего, и для аккаунта без почты. Различимый ответ превратил бы форму
восстановления в способ проверять, зарегистрирован ли ник.

Ранее выпущенные коды гасятся при выпуске нового: несколько действующих кодов
одновременно расширяют окно, в течение которого доступ к почтовому ящику даёт
доступ к аккаунту. Успешный сброс завершает **все** сессии.

### Уведомления

Уходят не на каждый вход, а только когда он выглядит необычно — новое устройство
или новая страна. Письмо на каждый вход приучает не читать уведомления, и настоящее
предупреждение о взломе прочитано не будет.

Отдельно уведомляются: смена пароля, изменение привязок, события безопасности
уровня `WARNING` и выше. Настройки — `mail.yml`, секция `notifications`, плюс
персональные флаги в таблице `emails`.

Шаблоны лежат в `<конфиг>/mail-templates/*.html`. Отсутствие файла не ошибка:
используется встроенный шаблон, потому что письмо о сбросе пароля важнее его вёрстки.
Значения подстановок экранируются — ник вида `<script>` не исполнится в почтовом
клиенте получателя.
